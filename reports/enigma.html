Executive Summary

Enigma exposed several externally reachable services, including HTTP, mail services, and NFS. Initial enumeration revealed an NFS share containing an onboarding PDF with employee credentials. These credentials allowed access to Roundcube webmail on mail001.enigma.htb, where additional internal credentials were discovered for an OpenSTAManager instance on support_001.enigma.htb.

OpenSTAManager was identified as version 2.9.8. Authenticated SQL injection was confirmed in /ajax_search.php, but the primary initial access path was an authenticated OpenSTAManager RCE involving crafted .p7m invoice upload filenames. The exploit produced a reverse shell as www-data. Post-exploitation enumeration revealed database credentials in config.inc.php. The application database contained bcrypt password hashes, and the hash for haris was cracked with Hashcat as bestfriends. This password allowed a local user pivot from www-data to haris and retrieval of the user flag.

Privilege escalation was achieved by identifying a local-only OliveTin service listening on 127.0.0.1:1337. OliveTin was running as root and allowed unauthenticated execution of actions. Its Backup Database action interpolated user-controlled values into a shell command. By injecting into the db_pass argument, a SUID copy of Bash was created at /tmp/rootbash. Running /tmp/rootbash -p produced a root shell and allowed retrieval of root.txt.

Completed attack chain: NFS credential leak → Roundcube mail access → OpenSTAManager admin credentials → OpenSTAManager authenticated RCE → www-data → database credential disclosure → bcrypt hash cracking → su haris → local OliveTin as root → Backup Database command injection → SUID rootbash → root.txt

Vulnerable Backup Action

- title: Backup Database
  id: backup_database
  icon: "⛁"
  shell: "mysqldump -u {{ db_user }} -p'{{ db_pass }}' {{ db_name }} > /opt/backups/backup.sql"
  popupOnStart: execution-dialog
  arguments:
    - name: db_user
      type: ascii_identifier
      default: backup_svc
    - name: db_pass
      type: password
    - name: db_name
      type: ascii_identifier
      default: production

The db_pass argument was inserted inside single quotes in a root-run shell command. By submitting a password value that closed the quote, appended commands, and commented out the remainder of the command, arbitrary commands could be run as root.

Payload

db_user: backup_svc
db_pass: x'; cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash; #
db_name: production

Resulting Command Behavior

mysqldump -u backup_svc -p'x'; cp /bin/bash /tmp/rootbash; chmod 4755 /tmp/rootbash; #' production > /opt/backups/backup.sql
The injected commands created a SUID-root Bash binary at /tmp/rootbash.

Lessons Learned

  • Externally exposed NFS shares are high risk: the initial foothold came from an unauthenticated NFS export containing onboarding credentials.
  • Email access often expands compromise: Roundcube mailboxes exposed additional internal application credentials.
  • Authenticated vulnerabilities still matter: OpenSTAManager required credentials, but weak credential handling provided those credentials early in the chain.
  • Configuration files commonly expose database credentials: config.inc.php provided the MySQL credentials needed for deeper enumeration.
  • Password reuse bridges application and system access: the cracked OpenSTAManager password for haris worked for the local Linux user.
  • Local-only services still matter: OliveTin was bound to 127.0.0.1, but it became accessible after gaining a shell.
  • Root-run automation must avoid shell interpolation: OliveTin executed a root shell command using user-controlled arguments, resulting in privilege escalation.

Remediation Recommendations

  • Restrict NFS exports to trusted hosts and remove sensitive onboarding material from shared drives.
  • Rotate all credentials exposed through NFS and email.
  • Enforce least privilege and avoid sending administrator credentials over email.
  • Upgrade OpenSTAManager to a version that patches authenticated SQL injection and authenticated RCE issues.
  • Implement strong password policies and prevent reuse between application accounts and Linux users.
  • Store password hashes using strong algorithms and monitor for weak passwords that appear in common wordlists.
  • Bind internal automation tools to authenticated interfaces and require login for all OliveTin actions.
  • Run OliveTin with a dedicated low-privilege service account instead of root where possible.
  • Avoid shell commands with interpolated user input. Use argument arrays, strict validation, and non-shell execution methods.
  • Review local services during hardening, even when they are bound only to localhost.
