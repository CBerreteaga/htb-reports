Executive Summary

The target exposed several services, including FTP, SSH, HTTP, and Minecraft. Initial enumeration showed that the web service redirected to blocky.htb and hosted a WordPress 4.8 site. Further web enumeration discovered a /plugins/ file browser that exposed downloadable Minecraft plugin JAR files.

The custom BlockyCore.jar file contained hardcoded database credentials. After extracting strings from the Java class file, a reusable password was discovered. WordPress author enumeration revealed the username notch, and the password from the JAR file was successfully reused to gain SSH access as notch.

Privilege escalation was straightforward after login because sudo -l showed that notch could run all commands as root. Using sudo, root access was obtained and the machine was fully compromised.

3. WordPress Enumeration

WPScan

The first WPScan attempt against the IP timed out because the application expected the hostname. Running WPScan against blocky.htb succeeded.

bash
wpscan --url http://blocky.htb --enumerate u,p,t --plugins-detection aggressive -o wpscan_enum.txt

Key Findings

WPScan confirmed:

  • WordPress 4.8
  • XML-RPC enabled at /xmlrpc.php
  • WordPress readme exposed at /readme.html
  • wp-cron.php enabled
  • Uploads directory listing enabled
  • Theme: twentyseventeen version 1.3
  • Plugin: akismet version 3.3.2

The uploads directory was browsable:

bash

Further enumeration found:

The exposed files were Minecraft wallpaper images. No credentials or code files were found in the uploads directory.

curl -Ls http://blocky.htb/plugins/

The page was titled:

Cute file browser

The JavaScript for this page called:

Querying scan.php exposed two downloadable plugin files:

curl -Ls http://blocky.htb/plugins/scan.php

Exposed Files

The BlockyCore.jar file was small and appeared to be a custom plugin, making it the most interesting file for analysis.

5. JAR File Analysis

The custom JAR file was inspected locally. Strings were extracted from the Java class file:

bash
unzip -p BlockyCore.jar com/myfirstplugin/BlockyCore.class | strings -a

Hardcoded Credentials Found

The extracted class strings revealed hardcoded database connection values:

text
sqlHost localhost
sqlUser root
sqlPass 8YsqfCTnvxAUeduzjNSXe22

This was the critical finding. The password was likely intended for local database access, but it was also worth testing for password reuse.

6. Username Enumeration

The WordPress REST users endpoint did not reveal users:

bash
curl -s http://blocky.htb/wp-json/wp/v2/users

It returned 404 Not Found.

WordPress author enumeration was then attempted:

bash
for i in {1..10}; do
  curl -sI -L "http://blocky.htb/?author=$i" | awk -v i="$i" '/^Location:/ {print i, $2}'
done

This revealed a valid username:

text
notch

At this point, the known credential pair was:

text
notch:8YsqfCTnvxAUeduzjNSXe22

Findings

Finding 1: Outdated WordPress Installation

Severity: Medium

The target was running WordPress 4.8, an outdated version with known public security advisories. While no direct WordPress exploit was required for this compromise, outdated CMS software increases the attack surface.

Evidence:

text
WordPress 4.8
Apache 2.4.18

Recommendation:

Update WordPress core, themes, and plugins regularly. Disable unnecessary WordPress features and remove unused plugins.

Finding 2: Directory Listing Enabled

Severity: Medium

Directory listing was enabled under the WordPress uploads directory and the custom plugin file browser.

Evidence:

text
/wp-content/uploads/
/wp-content/uploads/2017/
/plugins/

The uploads directory only exposed images, but /plugins/ exposed sensitive downloadable Java plugin files.

Recommendation:

Disable directory listing at the web server level. Sensitive files should not be stored in web-accessible paths.

Finding 3: Sensitive JAR File Exposed Through Web Server

Severity: High

The custom Minecraft plugin file BlockyCore.jar was publicly downloadable from the web server.

Evidence:

text
/plugins/files/BlockyCore.jar

This file contained application logic and hardcoded credentials.

Recommendation:

Do not expose application plugin files publicly. Store server-side application files outside the web root and restrict access to sensitive directories.

Finding 4: Hardcoded Credentials in Application Code

Severity: Critical

The BlockyCore.jar file contained hardcoded credentials.

Evidence:

text
sqlHost localhost
sqlUser root
sqlPass 8YsqfCTnvxAUeduzjNSXe22

Hardcoded secrets are dangerous because anyone with access to the source code or compiled application can extract them.

Recommendation:

Remove hardcoded credentials from application code. Use environment variables, secrets managers, or protected configuration files with strict permissions. Rotate the exposed password immediately.

Finding 5: Password Reuse Allowed SSH Compromise

Severity: Critical

The password found in BlockyCore.jar was reused for the system user notch, allowing SSH login.

Evidence:

text
Username: notch
Password: discovered in BlockyCore.jar
Service: SSH

Recommendation:

Enforce unique passwords across services. Use key-based SSH authentication where possible and disable password authentication for SSH.

Finding 6: Excessive Sudo Privileges

Severity: Critical

The user notch had full sudo rights.

Evidence:

text
(ALL : ALL) ALL

This allowed immediate privilege escalation to root.

Recommendation:

Apply least privilege. Users should only have sudo access to commands required for their role. Full sudo privileges should be limited to trusted administrators.

Lessons Learned

  • Always enumerate unusual web directories manually.
  • Follow redirects during web enumeration.
  • Small custom files are often more valuable than large third-party files.
  • Compiled Java files can still leak sensitive strings.
  • Password reuse is a common path from web findings to shell access.
  • sudo -l should be one of the first checks after getting a Linux shell.
  • Full sudo privileges usually mean root access is one command away.

Conclusion

Blocky was compromised through a chain of web enumeration, exposed application files, hardcoded credentials, password reuse, and excessive sudo privileges. The most important discovery was the exposed BlockyCore.jar file, which revealed a reusable password. Once the username notch was discovered through WordPress author enumeration, the password allowed SSH access. Full sudo privileges then allowed immediate escalation to root.

The main defensive takeaways are to avoid exposing sensitive files, never hardcode credentials, prevent password reuse, and enforce least privilege for sudo access.
